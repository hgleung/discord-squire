# Squire

A personal Discord bot. Runs on your own machine, in your own server, for you.

It's built as a small set of independent modules — each a directory under `src/modules` that owns some slash commands and whatever state they need. Two ship today; adding a third means adding a directory.

| Module | Commands | What it does |
|---|---|---|
| **assistant** | none needed, plus `/reminders` `/tasks` `/memories` `/usage` `/maps-todo` `/ticket` `/tickets` `/brief` `/voice` | A chat assistant: type in a listed channel and it answers, searches the web, sets reminders, and runs longer jobs in the background |
| **training** | `/today` `/log` `/split` `/splits` `/week` | A strength training log you can update from your phone at the gym |
| **system** | `/update` | Pulls the latest main from GitHub and restarts the bot |
| **music** | `/play` `/skip` `/queue` `/loop` `/shuffle` `/move` `/remove` `/clear` `/stop` `/music-help` | YouTube audio in a voice channel |

The training log and music are slash commands. The assistant is the one part that reads plain messages, so it needs Discord's Message Content intent, and the bot only asks for it while the assistant is switched on. It holds an outbound WebSocket to Discord — no inbound port, no tunnel, nothing hosted.

## Running it

```bash
npm install
cp .env.example .env      # then fill it in
npm start
```

`.env` needs a bot token and your Obsidian vault folder (`OBSIDIAN_VAULT`), where the training log lives. Everything else is optional. Commands are registered per-guild rather than globally, so they appear immediately in every server the bot is a member of — including one it joins later, with no restart needed.

**Only you can use it** if you set `DISCORD_ADMIN_ID` to your user ID. Anyone else gets a private refusal, and autocomplete stays empty for them so it can't leak what's in your log. Leave it blank to open the bot to the whole server.

A command can opt out of that with `public: true` — the whole music module does, so anyone in the voice channel can queue, skip, loop, or reorder. The training log stays yours.

## Assistant

List channel IDs in `ASSISTANT_CHANNEL_IDS` and add an `ANTHROPIC_API_KEY`, and anything you type in those channels gets a reply. There's no command to remember. With `DISCORD_ADMIN_ID` set, it answers only you. It also needs **Message Content Intent** switched on (Developer Portal → your app → Bot → Privileged Gateway Intents), or Discord refuses the login.

- **Memory is the channel.** Each reply reads the channel's last 30 messages (up to 12 hours back), so nothing is stored separately, a restart forgets nothing, and deleting a message removes it from what it remembers. Each channel is its own conversation, and the channel name steers the answer (#gym, #travel).
- **Web lookups** use Claude's built-in web search and fetch, and replies link their sources.
- **Reminders**: say "remind me to book the hotel Friday at 9" and it posts in that channel at that time and pings you. They can repeat (daily, weekdays, weekly, monthly) and live in `data/reminders.json`. If the PC was off when one was due, it fires late on startup and says so. `/reminders` lists them.
- **Background tasks**: bigger jobs, like "find me three hotels in Kyoto under $200 for those dates" or "watch fares to Tokyo and tell me if they drop under $800", go to a worker that keeps going after the reply and posts its report in the channel. Every task has a concrete *done when* condition and a hard deadline (at most 30 days out), and it ends at whichever comes first. A task that has to check back later saves itself to `data/tasks.json` and resumes at that time, even after a restart. Progress updates are capped, and so are API calls per task. `/tasks` lists them, and you can ask the assistant to cancel one. Each task also has a note in `Squire/Tasks/<date> <title>.md` from the moment it starts, so its state is in the vault: `status: todo | doing | done | failed` (couldn't finish and cancelled show as failed, with `outcome` saying which), `output: "[[Recipes/Meal/…]]"` linking the note it saved, plus `outcome`, `requested`, `finished`, `channel` and `tags`. You can also start one from Obsidian: write a note in `Squire/Tasks/` with `status: todo` in its frontmatter and a `Goal:` and `Done when:` (inline, bold, or as `## Goal` headings). Within 15 seconds it is picked up and run like one started from chat. Optional frontmatter: `channel: "#travel"` (default #misc, or #recipes when `job: recipe`), `tier: fast | capable`, `deadline` (default 24 hours). Only that note's frontmatter changes, and the report is added at the end, so your text stays as you wrote it. A note that can't start (no goal, unknown channel) is marked `failed` with the reason in `outcome`; set it back to `todo` to retry. Notes from before `status` existed get it added from their `outcome` on start, and nothing else in them changes.

Chat replies use `claude-haiku-5-5` at low effort, for speed. When the assistant starts a background task it picks a tier: research, comparison and planning go to `claude-sonnet-5-5`, and simple jobs like watching one number stay on Haiku. Tasks think at medium effort. Override the models with `ASSISTANT_MODEL` and `ASSISTANT_TASK_MODEL`. The conversation and tool format lives in `src/modules/assistant/llm.ts`. `anthropic.ts` is the only file that touches the SDK.

- **Gym talk uses the training log.** The assistant reads and writes the same log as `/today`, `/log`, `/split` and the web UI. Ask what's on today, what you lifted last push day or how your week looks, or just type "bench 185x5, 185x5, 175x6". It logs each set, loads the day's split first if needed, and points out new bests. Weekly numbers come from the app's own calculations, not the model's.
- **Factories**: a factory is one specific job Squire does over and over, with its instructions, state and results in the vault, where you can see and score them. The first is the **recipe factory**. A recipe reel, video or link posted on its own in #recipes becomes a `job: recipe` background task, which opens the link, writes a sourced note in the right `Recipes/` subfolder and reports back. The job's instructions are versioned notes in `Factory/Prompts/<job> vN.md`, with frontmatter `job`, `process_step`, `status: testing | production | retired` and `version`. A task runs the job's one `production` prompt (the highest version if you leave two in production), or the one it names: say "use recipe v2" in chat, or put `prompt: recipe v2` on a hand-written task note. On first start the built-in prompt is written out as `recipe v1` (production). With no prompt note, or none in production, the built-in prompt in `factory.ts` is used, so nothing breaks. Task notes record `job` and `prompt: "[[Factory/Prompts/recipe v1]]"`. Recipes from a photo, recipes you type out, and edits to an existing recipe stay with the chat.
- **Every job is a factory**: besides `recipe`, four jobs now have a job note, versioned prompts and starter eval cases (generic examples here; build your own from real history).
  - `research` is a task job for research, comparisons and trip planning; the chat picks it when it starts a task. It has 6 cases: parts of a trip-planning task (itinerary, comparing services, booking a small business, return routing, stays to book), plus sourcing recipe amounts.
  - `inbox-calendar` is the brief's step that adds booked events from email to the calendar. Its prompt is now a note. It has 7 cases, short made-up emails each aimed at a kind of inbox mistake (raffles, presale codes, pickup orders, transferred tickets, UTC times). Code checks the events and cancellations found against the expected ones.
  - `brief` covers only the wording prompt; the facts stay computed in code. It has 5 cases, each aimed at a wording rule. Code checks the length and Discord shape and catches "TBD" / "not set"; the cheap model judges the checklist.
  - `photo` is the photo actions, one per line in its prompt note as `- (tool group) what it shows => what to do`, still filtered by each channel's tools. Its eval cases are generated images (see below), since past photos weren't kept.
  - Code jobs run their one model call per eval case, so `npm run eval -- inbox-calendar` costs a few cents.
  - Photo actions have 6 starter cases, each an image beside its case note in `Factory/Evals/photo/` (a concert flyer, a coffee receipt, a ramen menu, a recipe card, a gym whiteboard, and a poster with no date). The image goes to the chat model with the photo prompt under test and the real tool definitions; nothing is run. Code checks the first action it takes (`expect_tool`, or `none` when it should ask) and that the details it read (`expect`) are in that call. Add your own photos as more cases: the image plus a note with `input: <image file>`, `expect_tool` and `expect`. `npm run eval -- photo --yes` costs a few cents.
  - `training-log` is the rules for logging sets you report in chat ("bench 185x5, 185x5, 175x6"). Its prompt note replaces the training section of the chat prompt, so a new production version changes how sets are logged with no restart. Its 6 starter cases (three bench sets, "squat 3x5 at 225", nothing loaded yet, yesterday's sets, bodyweight pull-ups, and a set with no exercise named) each run on a fresh training log in a temp folder, never yours, with the real training tools. Code reads back every set the log holds and compares it with `expect_sets` ("Back squat 225x5", "… @ 2026-11-19" for another day; empty means it should ask), and checks `expect_split` was loaded when given. `npm run eval -- training-log --yes` costs a few cents.
  - **Shadow periods.** `research`, `inbox-calendar` and `brief` start in shadow. In shadow, inbox-calendar finds events but doesn't touch the calendar: the brief says "Would add: …", a run note goes in `Squire/Tasks/`, and the emails stay unread so turning shadow off adds them. The brief in shadow still sends the production brief, and also words the same facts with the newest `testing` prompt, saving both side by side in a run note. Turn shadow off in each job note after a clean stretch.
- **Factory/ is yours**: `Factory/README.md` is your process note. The assistant and background tasks are told to read it when asked to build, run, review or improve a factory, and aren't sent its full text every time. The notes tools enforce in code that Squire reads anything in `Factory/` but writes only eval results (`Factory/Evals/<job>/results/`) and prompt notes that are and stay `status: testing`. It won't edit, move or trash production prompts, the README, job notes or eval cases unless your message names that note ("turn shadow off in the recipe job note"), and background tasks never can. Code that sets things up (the first `recipe v1`, job notes, the starter eval cases) only adds notes and never overwrites. The **Job registry** table at the bottom of the README is generated from code: job, status, shadow, production prompt and last eval pass rate. Only the table between `<!-- squire:registry -->` markers changes, on start and after each eval. The first time, `npm run factory -- registry` shows the edit as a dry run and `--apply` writes it. The Sunday weekly review gets a **Factories** section: each job's last pass rate and failed items, shadow results waiting for you, and any task `doing` for more than 24 hours.
- **Note types**: notes can say what they are with `type:` (project, trip, person, task, note, place, meeting), with fields Bases and Dataview can query; the schemas are written to `Squire/Ontology.md` and Squire uses them when it creates a typed note. `npm run vault:migrate` is a dry run listing every change it would make; `--apply` makes them and logs them to `Squire/Migrations/`. It only adds: a missing `type` where the folder already says it (Cafes → place, proj-ideas → project, Squire/Tasks → task), `trip: "[[Travel/<Trip>/<Trip>]]"` on notes in a trip folder, an index note for each trip and project folder (a table of its notes with their version or draft, regenerated only between `<!-- squire:index -->` markers), and moves of typed notes out of `Squire/Inbox` and `notes/` into their type's folder, with a redirect note at the old path when another note links to it by path. A field you set is never changed, and Training, Squire/Workouts, Factory and Recipes are left alone.
- **Read-only syncs**: every night (and with `npm run sync`) Squire writes snapshots into `Squire/Sync/`: `Calendar.md` (the next 60 days: time, title, place and calendar, never descriptions or guests), `Bookings.md` (Gmail's Reservations category from the last year, as received date, sender name, subject with confirmation and card numbers taken out, and a Gmail link, never the body; plus the upcoming events Squire added from email) and `Places/<name>.md` (one `type: place` note per spot on your Google Maps lists). `Sync status.md` says when each source last synced. Nothing in Gmail, Calendar or Maps is changed and no model is called, so it costs nothing. Unchanged notes aren't rewritten, nothing is deleted when it leaves the source, and a place note stops syncing once you take out its `sync: maps` line. The notes tools can't edit `Squire/Sync/`; chat reads the snapshots first and still uses the live tools for anything newer.
- **Vault lint**: `npm run vault:lint` checks every note in code (no model calls): broken `[[links]]` (attachments, links in code or frontmatter, and links to folders are skipped; case doesn't matter, as in Obsidian), two notes sharing a name, frontmatter that doesn't parse or a `type` no schema has, empty notes, `Squire/Inbox` notes older than a week, and tasks `doing` for over a day. It writes nothing; `--fix` makes the only fix that can't be wrong (a link to a redirect note left by a move becomes a link to where the note went) and writes the day's health note. Every night after the syncs, the bot runs it, makes that fix in its own notes under `Squire/` only, and writes `Squire/Health/<date>.md` listing everything else, including the fixes waiting in your notes.
- **Weekly vault health** (the `vault-health` factory): on the weekly review's day, after the lint, Squire lists candidate notes (untouched for 180+ days with nothing linking to them, almost empty, unfiled in `Squire/Inbox` or `notes/`, sharing a name, or named like a draft or version), never the training log, Factory, Archive or generated folders, and one call on the fast model proposes what to do: archive, file, merge or update. It writes them as a checklist in `Squire/Health/<date> proposals.md` and changes nothing else. Tick what you want and run `npm run vault:health -- --apply "Squire/Health/<date> proposals.md"`: ticked archives (to `Archive/`, keeping the path) and filings are made with a move, never a delete, and marked done; merges and updates rewrite notes, so ask Squire for them in chat. `npm run vault:health` shows the candidates and estimated cost, `--yes` runs it now. Like every job it has a job note, a versioned prompt and 5 starter eval cases (`npm run eval -- vault-health`).
- **Job limits, enforced**: a job note's `tools` is the only set of tools a job task gets (besides reporting back; add `web_search` or `web_fetch` to keep web access), `write_paths` the only folders its `save_note` may write, and `daily_cap_usd` the most it may spend in a day (default $3 for capable jobs, $0.50 for fast ones). Empty `tools` or `write_paths` means no extra limit. Spend comes from the activity log, which now records each job's runs on their own (`job:` on each event, the inbox step apart from the brief): over the cap, a running task stops, a new one isn't started, and the inbox step and the weekly vault health wait for tomorrow; the brief itself is never capped. `Factory/Registry.md` is generated on start, nightly and after each eval: every job's kind, trigger, tier, tools, write paths, shadow, production prompt, last eval pass rate, daily cap and cost over the last 7 days.
- **Improve loop**: after `npm run prompt:propose` writes a fix as a new testing prompt, `npm run improve -- <job> "<job> vN" --yes` runs the job's evals on it and on production (today's production result is reused rather than paid for twice; the cost is printed first), writes both results notes plus a comparison note (`<date> <job> vN compared.md`: pass rates, then case by case with fixed and broken cases first) in the job's results folder, and puts `eval_before`, `eval_after` and a link to the comparison on the testing prompt, which stays testing. Promoting is yours: set `status: production` on it and `retired` on the old one. `npm run factory -- trend <job>` prints the pass rate over time; the review digest shows the trend and any testing prompt that beat production and is waiting for you. Fixes that need code rather than a prompt still go through a pull request for you to merge.
- **Jobs are config**: each factory is `Factory/Jobs/<job>.md`, its prompts in `Factory/Prompts/`, and its cases and results in `Factory/Evals/<job>/`. The job note's frontmatter follows `Factory/README.md`: `trigger` (scheduled, event or manual), `channel`, `tools`, `write_paths`, `shadow`, `tier` (fast is the chat model, capable the task model), optional `effort`, `evals` and `review`. Model choice lives there, so changing a job's tier or effort needs no deploy. `npm run factory -- new <job> [--trigger …] [--channel …] [--what "…"]` builds a new job with no code: a job note, a first prompt (`testing` until you make it `production`) and an example eval case, and it never overwrites anything. The job then runs as a background task (`job: <job>` on a task note, or asked for in Discord). An eval case for any job can carry a `checklist:` of plain sentences, which the cheap model judges one by one. `npm run factory -- list` shows every job's kind, trigger, channel, shadow, tier, production prompt and last pass rate.
- **Shadow mode**: each job has a settings note, `Factory/Jobs/<job>.md`, written on first start. Its `shadow: true | false` is the recipe job's on/off switch, and the recipe job starts in shadow. In shadow, the job checks its note exactly as it would for real (the sources were read, the folder is right), then puts it in the task note under `## Proposed note`, with `shadow: true` and `proposed: "[[…]]"` in the frontmatter. It writes nothing to `Recipes/`, sets no reminders and saves no memories. The Discord report says what it proposes. Say "promote" (or "save it") and `promote_task` saves the proposal as it was checked, then sets `output` and `promoted` on the task note. It refuses if the target note appeared or changed since, so nothing of yours is overwritten. Set `shadow: false` in the job note to let it save directly; that takes effect from the next task.
- **Links both ways**: when a background task creates or changes a note, its task note's `output` points to that note, and the note gets `source-task: "[[Squire/Tasks/…]]"` in its frontmatter, pointing back. Notes the chat saves directly have no task, so they get no `source-task`. A promoted shadow proposal carries the link from the start. Obsidian's backlinks pane and Bases/Dataview queries can follow either direction.
- **Evals**: each factory has cases in `Factory/Evals/<job>/<case>.md`, with frontmatter `input` (the link or text), an optional `ask` ("cut it in half"), the `folder` it belongs in, and a `checks` list. The recipe job starts with 10 example cases (reels, recipe pages, a multi-sauce video, a pastebin paste and a recipe to halve), with placeholder links: replace them with posts from your own #recipes history. They are written on the first eval run, never overwritten, and are yours to edit or add to. `npm run eval -- recipe` prints the case count, the prompt and an estimated cost, then stops. Add `--yes` to run, and `--prompt "recipe v2"` to try a prompt that isn't in production yet. Each case runs as a real job task on the task model, in a temp copy of `Recipes/` and `Factory/Prompts/`, so nothing is written to your recipes. The note a case was built from (its `from`) is left out of the copy, so the job can't just find the answer already saved. Code judges *sources linked* (the input link is in the note, with a Source line or Sources section) and *right folder*. The chat model (the cheapest tier) judges *estimates labeled*, *units consistent* and *no invented amounts* against what the job actually read; a scaled amount rounded to a kitchen measure counts as scaled, not as an estimate. A case passes when every item does. The table goes to `Factory/Evals/<job>/results/<date>.md`, with `pass_rate`, `failed_items` and the cost in its frontmatter, plus each case's reasons and the note it would have written (or, when it saved nothing, its report).
- **Memory**: the assistant keeps short facts that will make later answers better, like your gym split, preferences, people and routines. It saves them on its own, or when you say "remember…". It updates or forgets them when things change, or when you ask. Every memory goes into every reply and background task. They live in `data/memory.json` (capped at 200 short entries), and `/memories` lists them. Memory is for the assistant; notes you'll open yourself go to Obsidian.
- **Journal**: when a channel has been quiet for 30 minutes, the conversation is summarised into `data/journal.json`: what it was about, the specifics (dates, bookings, places, prices), what was decided and saved where, and what's still open. The first run reads back 10 days. Every reply sees the latest few summaries plus any plan with a date still ahead (a trip stays in view until it ends), older summaries that share words with your message ride along with it, and `recall` searches the rest. So a Tokyo restaurant reel days later lands on the Japan trip without you explaining it again.
- **Activity log**: every reply, background task, journal run and morning brief adds a line to `data/activity/<date>.jsonl`: the start of what you asked, which tools ran and which failed with what error, how long it took, the tokens it used and an estimated cost. It's the per-message half of the journal (which keeps what each conversation was about), so between them nothing is stored twice. It stays on this PC, never in the vault, and days older than 120 are deleted. `/usage` adds up spending by day, by kind and the priciest jobs, from list prices; the Anthropic console has the real bill. `npm run review:digest -- <since>` prints the journal and the activity since a time, problems first, for the daily review. With `OBSIDIAN_VAULT` set it ends with a **Factories** section. For each job it shows the production prompt, shadow on or off, and any testing prompts; the latest eval pass rate and the three before it; each eval case and real run since then that failed a checklist item (code checks a real run's sources against the link it was given); and the shadow proposals waiting for you. The review proposes a prompt fix with `npm run prompt:propose -- <job> <file> "<what it fixes>"`. That always writes a new `<job> vN.md` with `status: testing`, `based_on` and `why`, and never edits the production prompt. Then it runs `npm run eval -- <job> --prompt "<job> vN" --yes` to compare. Moving a prompt to production is up to you: set its `status: production` and the old one's to `retired`.
- **Voice notes**: a Discord voice message (or any audio file you attach) is transcribed on this PC with the same Whisper model used for reels, and the transcript stands in for the message from then on, in later replies and in the journal too. Transcripts are kept in `data/voice.json`. Notes over 10 minutes are skipped.
- **Morning brief**: at 8 AM (`MORNING_BRIEF_HOUR`), #misc gets one message (or `MORNING_BRIEF_CHANNEL_ID`; #misc is found by name once and then kept by ID, so renaming it is fine) with today's weather (Springfield, plus Portland around 100 Main St (97204) on weekdays), your calendar and reminders for today, anything in the last day's mail that needs you (Gmail's promotions and social tabs left out), what the journal says you still have to do this week (leaving out anything a reminder already covers, anything you've dropped, and alerts or suggestions you never took up), open decisions for trips more than a week out in their own **Open travel decisions** section, and how many spots are waiting to be saved in Maps. Before writing it, the bot reads the last three days of mail for things you've booked or bought tickets for (a concert, a reservation, an appointment, a flight) and adds each one that isn't on your calendar yet to the main account's primary calendar, then says so under **Inbox**. Each email is read for this once, and an event already on the calendar that day under a similar name is left alone. When a later email says you're no longer going (a refund, a cancellation, a ticket you transferred or sold), an event Squire added is taken off again; one you added yourself is left, and the brief points it out. Raffle entries, sign-ups that aren't tickets, invitations to register and "your event is coming up" reminders are ignored. The facts are gathered by the bot; the chat model only words them, and the weather lines are put on top by code (a neighbourhood with no forecast of its own falls back to its city). Tell it an item is done or not worth listing ("the lyft login was me") and it's dropped from later briefs for 90 days. A PC switched on later in the morning still gets it, until 1 PM. `/brief` sends one now.
- **Tickets**: right-click (or long-press) any message → Apps → **Ticket**, and say what's wrong with it; or `/ticket note:<what's wrong> message:<link or ID>` (leave `message` out for Squire's latest message in the channel). Tickets keep the message, the ask it answered and your note in `data/tickets.json`. `npm run review:digest` lists open ones first, so the nightly review handles them, and closes each with `npm run tickets -- close <id> "<PR link, or why not>"`. `/tickets` lists the open ones.
- **Obsidian notes**: "save this recipe to my notes" writes a note to `Squire/Inbox/` in your vault, or to any folder you name. It organises the whole vault as you ask: makes folders and subfolders, moves and renames notes and folders, and puts notes in Obsidian's trash. It can also search and read any note ("what's on my packing list?"), and never touches Obsidian's own dot-folders. Its own files live in `Squire/`: the inbox is its own scratch space, it leaves `Training/` and `Squire/Workouts/` to the training log, and every background task keeps its note, status and report in `Squire/Tasks/<date> <title>.md` (see Background tasks), and the Discord message says where.
- **Gmail and Calendar** (optional): search and read mail, save drafts (it never sends), and read, create, change and delete calendar events. Setup is a Google Cloud OAuth client (Desktop app) with the Gmail and Calendar APIs enabled, then `npm run google:auth` once. `.env.example` has the steps. More Gmail accounts can be added for mail (`GOOGLE_EXTRA_ACCOUNTS=work`, then `npm run google:auth -- work`): searches cover every account unless one is named, and the morning brief checks each inbox with the same filter. Background tasks get read-only access. Email and invite text comes from strangers, so the assistant is told to treat it as information and never as instructions. Even so, a hostile email can try to steer it. That's why it can't send, and why unattended tasks can't write anything. The one exception is the brief adding booked events from the inbox: the worst a hostile email can do there is put up to five events on your calendar, each noting the email it came from.
- **Saved places** (optional): your Google Maps lists (Food, Bars, Dessert, Cafes) back "dessert near Mission Dolores", "a cafe open now to work from" and "what's good in Vegas". Google has no API for saved lists. Each list is read from its share link (`MAPS_LIST_URLS`) through the unofficial endpoint the list's own web page uses, every 6 hours, into `data/places.json`. A failed read keeps the last good copy, and `places_lists` shows the error. With `GOOGLE_MAPS_API_KEY` (Places API (New)), each spot gets its hours, rating and price, looked up once and refreshed monthly. That makes "open now", "near <anywhere>", adding spots by chat ("save Tartine to dessert") and looking a shop up without saving it (`places_lookup`: "where's COOR's Seongsu store, and when's it open?") possible. Spots added by chat go into the existing list that fits (a new list only if you ask for one by name) and live in Squire's copy only, since Maps can't be written to; the reply carries the Maps link so saving it there is one tap. `/maps-todo` lists every spot still waiting to be saved in Maps, with its link, and each drops off on its own once the next sync finds it in the Maps list. When a calendar event today is more than 80 km from home (an all-day "Stay at a hotel in Chicago", say), the first assistant channel gets one morning message with your saved spots there.

- **Writes like you**: Squire reads your own messages in every channel, voice channel chat and thread it can see, in the servers you share with it, and writes its replies, task reports and the brief the way you text. Only messages you wrote are kept (`data/style.json`, the newest 20,000); nobody else's text is stored. Commands, code, link-only messages, pastes over 500 characters and anything with an email address or a long number are skipped, and mentions become "@someone". It runs once on its own, a few minutes after the first start: it reads every channel back to its start, then the task model reads a sample (mostly what you said to people, some of what you said to Squire) and writes a style guide with counted habits (capitals, punctuation, length, emoji), and picks about 30 of your messages, by number so they stay verbatim, as examples. Those go in the prompt; nothing is fine-tuned. `/voice show` shows the guide and examples, `/voice refresh` reads what's new and rebuilds (nothing reads or rebuilds on a timer), `/voice off` and `/voice on` switch it. It needs `DISCORD_ADMIN_ID`, so it knows whose messages are yours, and the bot needs View Channel and Read Message History wherever you want it to read. `ASSISTANT_VOICE=off` turns it off.
- **Weekly review**: on Sunday (`WEEKLY_REVIEW_DAY`) the morning brief becomes a weekly review: today's sections, then the week ahead by day, the training week just ending (the app's numbers), what the week's replies cost, and up to three memories a recent conversation suggests are out of date.
- **Search by meaning**: notes and journal entries are embedded with a local Ollama model (`nomic-embed-text` by default: `ollama pull nomic-embed-text`) into `data/semantic.json`, re-read every 30 minutes, embedding only what changed. `semantic_search` finds things by what they're about ("that dumpling place Chris mentioned"), and up to two older conversations about the same thing ride along with each message even when they share no words with it. With Ollama off, the keyword tools still work.
- **Photos**: a photo or screenshot with no ask becomes what it's for: an event flyer or ticket goes on the calendar, a receipt goes into the month's expense note (`Finance/Expenses/2026-11.md`, also `log_expense` when you say what you spent), a place gets saved, a recipe page becomes a recipe note, a gym whiteboard gets logged, handwriting becomes a note. The list lives in `PHOTO_ACTIONS` in `photo.ts`, so adding a kind is one row.
- **Channel tools**: channels in the `squire` category (`ASSISTANT_TOOL_CATEGORY`) get only the tools their name calls for: #gym the training log, #travel Gmail, Calendar and places, #recipes notes and places. Reminders, memory, the journal, tasks, links and web search work everywhere, and unmapped channels get everything. `ASSISTANT_CHANNEL_TOOLS="cards=google,notes"` changes or adds one.

`ASSISTANT_LOCATION` sets your default location. Searches are localised to it, and "the weather" means there unless you say otherwise. `ASSISTANT_ABOUT_ME` is a line of anything else it should always know about you. Both live in `.env`, so they stay off GitHub. `npm run check:assistant:live` makes one real round trip, a web question plus a reminder, without Discord.

## Training log

Log what you trained: the exercises, and for each set the weight, reps, and whether you hit it.

- **Splits, not schedules.** `/split Push day` loads that session's exercises. Nothing is tied to a clock — an exercise is a list of sets.
- **Weights carry forward.** Loading a split pre-fills each exercise with what you lifted last time, left unticked so you confirm each set.
- **`/log bench 140 6`** fills the next unticked set. Extra sets beyond the plan are appended, not refused. It tells you when a set is a new best.
- **The headline metric is hard sets per muscle group per week**, which is the variable you actually program against and the one a PPL split hides — "all sets done" while your rear delts got four and your triceps got twenty-eight. Load progression is tracked per lift via estimated 1RM, so a heavy triple and a set of ten are comparable.
- **The log is markdown in your Obsidian vault**, and those files are the source of truth. Each split is a note in `Training/Splits/` and `Training/Training.md` holds the plan name, unit and quick-add exercises, both next to your own notes. Each workout is its own note in `Squire/Workouts/` (`2026-11-12 Workout.md`). A set is a checkbox line (`- [x] 185 lb × 5`; `—` marks a weight or reps not yet entered), so ticking it in Obsidian logs it. Under each exercise heading, one line carries the target, muscles and colour (`Target: 4 × 6 · Primary: Chest · Secondary: Triceps · Color: red`). Any other line is that exercise's note. A heading you add by hand becomes an exercise. Edits you make in Obsidian show up in Discord and the web UI within a second or so. Text outside those shapes, like a paragraph above the first exercise, is dropped the next time the bot writes that note. A file that won't parse is skipped with a warning and never deleted.

`/week` writes a summary of the week — days trained, which muscles landed in or under their target range, which lifts moved. It runs through a **local model via [Ollama](https://ollama.com)**, so nothing leaves your machine:

```bash
ollama pull qwen2.5:7b
```

The numbers in that summary are computed by the app, not the model. Asked to restate them, a 3B model reported a +10.8% squat PR as "held" in three runs out of three; the model gets the prose, the figures are rendered directly. `qwen2.5:7b` is the tested recommendation — it quoted set counts and target ranges correctly where `llama3.2` carried one muscle's figures onto another's line every run.

### Optional web UI

`web/` holds a browser UI for the same log: a muscle-volume chart, per-lift progression, and a split editor. It's off by default.

```bash
# .env
WEB_PORT=4000
```

```bash
npm run web          # dev server on :5173, proxies /api to the bot
npm run web:build    # after which the bot serves it at :4000 directly
```

The bot owns the log; the UI is a client of it. Every write carries the revision it was based on, so a set logged from Discord can't be overwritten by a browser tab that was open at the time — the tab adopts the newer copy instead. Server-sent events push changes the other way, so a set logged from your phone, or ticked in Obsidian, appears in an open tab without a refresh. The UI's "Save as file" still downloads the whole log as JSON, which works as a backup, and `npm run training:import -- <file.json> "<vault>/Training"` turns such a file back into notes in an empty folder (workouts land in its `Workouts/`).

## Music

`/play` takes a link or search text, joins your voice channel, and plays. Playlist links queue up to 50; a video link copied from inside a playlist plays just that video. `/shuffle` reorders what's queued, `/move` sends a track to play next or last, `/remove` drops one — both by its number in `/queue` — and `/clear` empties it while the current track keeps playing. It leaves on its own after two idle minutes. `/music-help` lists every music command with its arguments, generated from the commands themselves so it can't drift out of sync.

Tracks run into each other without a gap. Opening a stream costs a second or two — yt-dlp's signature solve, then ffmpeg probing the container — so the next track is opened while the current one plays and sits back-pressured with about a second of audio already decoded. Reordering the queue retargets it; the check confirms that for move, shuffle, and remove.

`/loop` never downloads twice. The bytes are kept in memory as a track plays, and a loop replays them — YouTube refused a rapid re-download of a track that had just played through with a 403, and a second fetch is wasted work regardless. Live streams are the exception: they never end, so they're neither buffered nor prefetched.

**Age-restricted videos** are skipped with "Sign in to confirm your age" unless yt-dlp has a YouTube login. `YOUTUBE_COOKIES` (a cookies.txt exported from a signed-in browser) or `YOUTUBE_COOKIES_FROM_BROWSER=chrome` in `.env` provides one. yt-dlp then acts as that account, so a throwaway is the sensible choice.

Audio comes through [yt-dlp](https://github.com/yt-dlp/yt-dlp) and a bundled ffmpeg, so nothing needs installing beyond `npm install`. YouTube requires solving a JavaScript challenge to get valid media URLs; yt-dlp is pointed at the Node the bot runs on for that, without which every video resolves and then plays silence.

**Two things to know.** Streaming YouTube this way is against YouTube's terms of service; the bot this was ported from ([maxcutlyp/YoutubeBot](https://github.com/maxcutlyp/YoutubeBot)) exists because the big hosted music bots were taken down for exactly this. Self-hosting privately is the lowest-risk form of the same activity, not a different one. And yt-dlp is in a permanent cat-and-mouse with YouTube — when playback breaks with no code change, `npm update youtube-dl-exec` is the first thing to try.

## Updating

`/update` (owner-only) fetches main from GitHub, fast-forwards the checkout the bot runs from, runs `npm install` if the lockfile changed, and exits so the Windows launcher starts it again on the new code. It refuses, and changes nothing, when the checkout is on another branch or has local changes. `.gitattributes` keeps Windows line endings from counting as local changes.

## Adding a module

A module is a directory under `src/modules` exporting a `BotModule`: a name and a list of `Command`s, each pairing a `SlashCommandBuilder` with a `run` function. Throw from `run` to fail — the dispatcher turns it into a reply. Register it in `src/index.ts`.

```
src/
  index.ts           entry: config → vault → modules → bot → optional web API
  bot.ts             client, command registry, owner gate, dispatch
  config.ts          typed .env
  vault.ts           the Obsidian vault: safe paths, unchanged-skipping writes
  modules/
    types.ts         the BotModule and Command contracts
    assistant/       chat agent, background tasks, memory, notes, Gmail/Calendar;
                     llm.ts is the conversation/tool core, anthropic.ts the API adapter
    training/        log commands, the markdown plan store, the web API
    music/           player, yt-dlp resolution
    system/          /update
lib/                 domain logic shared by the bot and the web UI
web/                 the optional React UI
```

`lib/` is deliberately neutral — scoring, e1RM, plan validation, and the summary prompt live there so the bot and the web UI cannot drift apart. It is plain TypeScript with no Node or browser APIs.

## Checking it works

```bash
npm run typecheck
npm run check        # training smoke, music pipeline, queue/prefetch, loop-from-memory
```

The training smoke test exercises the markdown store (round trips, a checkbox ticked on disk, a hand-added exercise, a renamed split) and every command's logic against a temporary folder. The assistant check covers the conversation as the Messages API receives it, background tasks against a scripted model, memory, notes, and the Gmail message building and parsing. The music check resolves a search and each way a video link gets pasted, then decodes three seconds of audio through the full pipeline. Together they cover everything short of the Discord connection and the live APIs. `npm run check:assistant:live` makes one real round trip to Claude.

Built with discord.js, @discordjs/voice, yt-dlp, and Express. The web UI is React, Vite, and Tailwind.
